# PPT 工作室 · 文案手册

> **优先级**：用户指令 > 本手册经验值 > 工具默认。用户明确给了语气、字数或既有定稿 → 一律照用户的。
> **范围**：只谈"怎么写人话"。**不定义字数下限/上限等门禁数值**——页面放不放得下由 `ppt_verify` 的溢出判定说了算。
> **互操作**：技能目录里若有 humanizer / 去 AI 味类技能，**优先用那一本**，本手册作为兜底与"页面文案专用"的补充。
> **标签约定**：`经验值（可覆盖）`＝参考，可被内容或用户要求推翻；不带标签的祈使句才是要遵守的做法。

## 1. 先判断要不要动笔

```
你要做的是？
├─ 写新页面文案 → §3 定型，再按 §4–§6 过一遍
├─ 用户说"太 AI 了" → §4 成组信号逐条比对，只改命中的（别整页重写）
├─ 只是页面放不下 → 先砍信息（§3），不要先缩字号
├─ 讲稿（**不进 pptx**，见 §7 前提）→ §7
└─ 用户给了明确语气或已有定稿文案 → 照用户的；不要"顺手润色"已定稿
```

## 2. 铁边界：只改文风，不动事实

改写**不得**新增、删除或修改任何数字、来源、时间、人名、机构、术语。
需要新增证据时，回去问数据来源，不要为了句子顺而编一个。

```
✗ 原文「试点 6 组，闭环率 94%」 → 改写后「多家试点团队闭环率超过 90%」   （把精确事实改成了模糊表述）
✓ 原文「试点 6 组，闭环率 94%」 → 改写后「6 组试点，闭环率 94%」          （保留全部事实）
```

## 3. 页面文案的三种角色（写法各不相同）

| 位置 | 任务 | 写法 |
|---|---|---|
| 标题 | 说出结论 | 主谓完整、可读、带数字或判断；不用名词堆 |
| 要点 | 给证据碎片 | 数字/事实/对比；一条一个点；不写形容词 |
| 注释 | 交代口径与条件 | 来源、范围、单位、假设；不发表感想 |

**解释与推理进讲稿**（§7）。页面文字是"结论 + 证据"，不是"文章"。

**给既有稿补文案时**：先读该册已定页的称呼、术语、数字写法与语气，沿用同册习惯；
不要在一个已经定稿的册子里引入另一套风格（一致性优先于你更喜欢的写法）。

## 4. 成组信号清单（**同一段里成组出现才改**，单个词不算）

改写判据是"信号**成组**出现"：单独一个「此外」不用动，一段里同时有夸张意义 + 三段式 + 破折号揭示，就必须改。
（**"成组"的口径 = 同一段里命中下表的 ≥2 类信号**；上面那串例子列了 3 类，不是说 2 类不算。）

| # | 信号 | 诊断 | 改法 |
|---|---|---|---|
| 1 | 作为/标志着/见证了/是…的体现/里程碑 | 给事实加了仪式感 | 直接写事实与幅度 |
| 2 | 突出/彰显/确保/赋能/助力（-ing 式收尾） | 用动词代替结论 | 写"改了什么、结果如何" |
| 3 | 充满活力/坐落于/令人瞩目/业界领先 | 宣传腔 | 换成可核验的描述或删掉 |
| 4 | 行业报告显示/专家认为/普遍认为 | 模糊归因 | 说出具体来源与样本，或删 |
| 5 | 「挑战与展望」「机遇与挑战」式小节 | 公式化收尾 | 写具体的未解问题与下一步动作 |
| 6 | 此外/与此同时/值得注意的是/深入探讨/格局 | 填充与膨胀 | 大部分可直接删；连接词不超过必要 |
| 7 | 作为/代表/充当/拥有…（回避"是/有"） | 系动词回避 | 用「是」「有」 |
| 8 | 不仅…更是…／不是…而是…／既不…也不… | 否定式排比 | 拆成两句，直陈事实 |
| 9 | 三项并列凑成一组（尤其三词同构） | 凑数三段式 | 删到真实项数；两项就写两项 |
| 10 | 从…到…（并非真的范围） | 虚假范围 | 写明确的两端或改为举例 |
| 11 | 同一意思换词重复（提升/优化/改善轮着用） | 同义词循环 | 一个概念固定一个词 |
| 12 | ——（破折号揭示）、粗体标签+emoji 装饰 | 修辞代替结构 | 用分句与层级代替标点花活 |

## 5. 结构级信号（比用词更容易被识破）

- **通用积极结尾**：「未来可期」「持续向好」「迈上新台阶」→ 换成下一步动作与负责人/时间。
- **三段式套路**（背景—问题—方案—优势—规划—总结 每份都长一样）→ 按内容真实结构排页（页序判据见 `ppt-studio-craft` §3）。
- **空转的过渡段**：「让我们来看一下…」→ 页面不需要过渡句，直接给内容。
- **形容词密度 > 事实密度**：一句里形容词超过两个（经验值（可覆盖）），通常该删。

## 6. 节奏六问（改完通读一遍）

1. 连续三句都是同样长度？→ 打散长短。
2. 是否用一句"金句"收尾？→ 换成具体动作或数字。
3. 破折号是不是用来制造"揭示感"？→ 改成两个短句。
4. 有没有比喻被解释了？→ 删掉解释，或删掉比喻。
5. 段首是否都是「此外/然而/因此」？→ 删连接词，让内容自己衔接。
6. 是否凑了三项？→ 删到真实项数。

## 7. 讲稿怎么写（**插件不会把它写进 pptx**）

**先明确交付通道**：本插件**不生成备注页**——导出的 .pptx 里没有 notesSlide；
`ppt_import` + `ppt_splice` 只**保留源文件该页既有的**备注关系（`ppt_splice` 输出里会写"备注关系：保留/源该页无备注"），
在 `deck.yaml` 写 `notes:` 也不会进 pptx（那只是工程内记录）。
所以讲稿要落成**交付说明或单独文件**，交付时告诉用户它放在哪。
下面是"讲稿该写成什么样"的标准，与它最终存在哪个文件无关。

页面放"结论 + 证据"，讲稿放"推理 + 过渡 + 被砍掉的细节"。
讲稿用口语短句，允许不完整句；一页讲稿对应页面上的一条论证线，不重复页面文字。

**结构化写法**（四段，缺哪段就补哪段）：

1. **本页目的**：这一页要听众得到什么（一句话）。
2. **讲述要点**：3–5 条（经验值（可覆盖））**提词卡式**短句——写"讲什么"，不写逐字稿（逐字稿会让人念稿）。
3. **转场**：为什么下一页紧接出现（一句因果，不是"接下来我们看…"）。
4. **现场提示**：停顿点、要互动的问题、翻页时机、万一被追问的备用说法。

**两个容易混的东西要分开写**：讲述计划时长（你打算讲多久）与自动翻页秒数（放映设置）不是一回事——
**后者不在本插件范围**（DSL 里没有翻页/计时字段），需要时由用户在 PowerPoint 里自己设。
**讲稿用稳定的页面标识做键**（页面 elementId/文件引用），不要用页码——中间插页或重排后，按页码挂的讲稿会串页。

## 8. 中英混排与术语

- 术语全册统一（同一概念别一半中文一半英文）；产品名/缩写按用户给的写法保留，不要自行翻译。
- 中英之间加空格与否，跟随该册已有页面；不要同一册两种写法。
- 数字与单位之间、百分号前的空格同样跟随既有页面。

## 9. 五组 before → after（可直接对照学习）

| # | 改前 | 改后 |
|---|---|---|
| 1 | 本次更新作为团队创新的有力证明，不仅优化了性能，更重塑了协作格局。 | 导出从 40 秒降到 6 秒，并加入批量替换。 |
| 2 | 方案坐落于行业前沿，拥有丰富的应用场景与令人印象深刻的扩展能力。 | 支持 3 种输入格式，单次约 1 万页；更多格式下一版。 |
| 3 | 这不仅仅是模板替换，而是对演示逻辑的重新思考——确保每页高效传达。 | 换了模板，并按「问题→证据→结论」重排页面。 |
| 4 | 专家认为该方法在复杂场景下具有关键作用。 | 我们在 12 组真实稿上试跑，9 组一次通过门禁。 |
| 5 | 尽管面临诸多挑战，项目仍持续蓬勃发展，未来可期。 | 还有两处几何门禁未清零，计划本周修完。 |

## 10. 交付前自检（每条都能"数出来"或"对照原文"）

| # | 检查 | 怎么核对 |
|---|---|---|
| 1 | 标题能读出结论 | 只读标题抄成一行；读不出来的标题数 = 0（改不出来 → `ppt-studio-craft` §4） |
| 2 | 事实零改动 | **逐句回读**：把改后文字与原句并排看——数字、单位、时间、来源、限定条件（"多数""试点")有没有为了顺口被改掉 |
| 3 | 成组信号已清 | 按 §4 的 12 类逐段扫：同一段里命中 ≥2 类的段落数 = 0 |
| 4 | 结构级信号已清 | 通读一遍回答 §6 的六个问题，任何一问命中就回去改 |
| 5 | 页面/讲稿分工 | 页面上还有解释性长句（本该进讲稿）= 0；文字溢出以 `ppt_verify` 输出为准，不靠猜 |
| 6 | 全册一致 | 术语、中英空格、数字格式：抽查首尾各两页对比，不一致 = 0 |
| 7 | 讲稿四段齐、且落在对的通道 | 每页讲稿：目的/要点/转场/现场提示四段都在；用稳定页面标识做键（不是页码）；**讲稿写在交付说明或单独文件里**——插件不导出备注，别以为它能进 pptx |

> 第 2、7 条是"红线"——改文风绝不动事实；这两条不过不交付。

## 11. 什么时候不要用本手册

- 版式与页序问题（那是 `ppt-studio-craft`）。
- 图表/数据呈现（`ppt-studio-data`）。
- 用户已定稿或明确语气要求 → 照用户的，不做"顺手润色"。
- 技能目录里有 humanizer 类技能且任务就是整体去 AI 味 → 用那一本，本手册只处理页面结构相关部分。
