# 05 · 迭代流程（每次改动的检查单 + Git/发布约定）

## 一次迭代的标准循环（推荐顺序）

1. **读文档**：`docs/01-需求与目标.md`（冲突清单 C* 是否受影响）+ `docs/04-路线图.md`（本迭代目标）。
2. **定目标**：1 个主目标 + ≤3 个小修；写进 `docs/03-更新日志.md` 待办行。
3. **改代码**：只改 `src/`（lib 由 build 生成，勿手改）。
4. **同步文档**（铁律，缺一不可）：
   - `docs/02-技术报告.md`：模块/机制/契约变了就改；波及面速查表对应行打勾。
   - `docs/01-需求与目标.md`：需求/决策/冲突清单有变化就改（推翻决策必须写"为什么"）。
   - `README.md`：使用者可见的行为变化（工具面/参数/规则/子集表）。
   - `src/scaffold.js` `SCHEMA_REF`：DSL 语法有变化就改（与 README/技术报告三处一致）。
   - 工作流提示词（`src/router.js`）：铁律/入门段有变化就改（模型看到的 = 文档）。
5. **构建**：`node scripts/build.mjs`（src → lib）。
6. **回归**：
   - `node scripts/smoke.mjs`（必须全绿；新增特性 → 增量断言，坏例优先"先写失败测试"）。
   - `node scripts/regression-real.mjs`（真实资产：19 页 deck + WPS fixture）。
7. **生效**：首选**重启 DSH host**（保底且干净——注入器注册表自动恢复全部插件；无任何挂起状态）。
   - 备选：`dev_reload_package dsh-ppt-studio`——**已知缺陷（2026-09-04 排查）**：build 后立即手动重载与 watcher 自动重载并发时，`ctx.loader.import` 可能产生"僵尸 in-flight job"，同 URL 后续 import 永久排队 → 工具调用卡死（注入器已加超时/锁/cache-bust 三重防护，但**僵尸 job 通道为宿主侧限制，不能保证 100% 免疫**）。**实践经验：build 后若 30 秒内 watcher 自动重载未完成，直接重启，不要反复手动重载**。
   - **新增事实（2026-09-05 确认）**：本插件经 agent preset 行**会话级装配**（include 机制），不在注入器 loader 域——`dev_reload_package` 无法命中（重载空转），`dev_plugin_status` 也不显示。**改码 → 重启 host 是唯一可靠生效路径**（注入器 0.3.4 起该工具会给出明确诊断）。
8. **记录**：`docs/03-更新日志.md` → `## [版本号] 日期` 目的/改动/验证/影响；改 `package.json` version（semver）；git commit（message 含版本号）。

## 装配注意（2026-09-04 教训入库，v0.14.2）
- **本插件有两个装配源**：注入器 registry 恢复（host 启动）+ agent preset 插件行（agent 挂载）——同包可能装配两次（时序竞态曾导致 duplicate 路由崩溃）。
- **凡 host 资源注册（webServer 路由等）必须幂等**：globalThis refcount（模块级变量在 junction/真实路径双加载下不可靠）——见 preview-server.js ROUTE_REG 范式（首个注册者真注册、最后卸载者真卸载）。
- 新资源注册一律 `ctx.effect`（清理即净）。

## 装配定论（2026-09-05 定；**2026-09-24 按 DSH 0.1.7 改判**）
- **装配源 = profile bundle 行（唯一）**：包的 `cordis.patch.yml`（`dsh.bundle.patch`）插入 `id: ppt-studio` 行 → profile 级 ⇒ 该 profile 所有会话都能用。
- **预设 = 注册表声明**（不是磁盘目录）：插件激活时 `ctx.agentPresets.register({id:'ppt', …})`，`plugins` 取自包内 `agent-presets/ppt/agent.cordis.yml`。0.1.6 及以前"写 `<dshHome>/.agent-presets/ppt/`"的做法在 0.1.7 上**没有任何效果**（上游不再扫描目录），安装器会清理该历史目录。
- **注入器 registry 的 ppt-studio 记录已清除**（历史残留，来源：09-03 dev_inject_plugin 实验）——保证永不出现双源。历史 junction（`profiles/web/node_modules/@dsh-external/dsh-ppt-studio`）**不要保留**：包名已改无 scope，且 0.1.7 的装配不再需要任何 junction。
- **开发工具的现实约束**（注入器 0.3.4 起已诊断化）：`dev_reload_package` / `dev_plugin_status` 只覆盖注入器 loader 域；bundle 行装配不在其中 → 改码 = 重启 host；`dev_build_plugin` 不再把 DSH_CHECKOUT 当构建前置（copy-only 插件无需 checkout；需要 tsc 的插件由其 build.sh 报明确错误）。
- **yaml@2 节点 API 教训**：`parse()`（纯值）/ `Document.toJS()`（Document 级纯值，推荐）/ `doc.get()`+`node.toJS()`（AST 层，裸 toJS 抛 "A document argument is required"）——parseDocument 场景读值一律 `doc.toJS()`。

## 装配与安装（2026-09-14 新增 profile bundle 路径后）
- **两条路径，二选一**：① `dsh plugin --profile <p> add <包>`（走包里的 `cordis.patch.yml`，**profile 级**）；② `install.mjs` 写 agent preset 行（**会话级**）。
  同时装 = 同进程挂两次 → 插件有**装配防重**（首个生效 + 告警）不会崩，但纪律是二选一（README §0.7）。
- **"能不能用标准姿势装"取决于包自己**：依赖必须声明 `dsh.bundle.patch`（且该文件在 `files` 里），否则 `dsh plugin add` 只装不挂、仅打一行警告。
  改这件事后**必须跑 `npm run test:bundle`**（隔离 DSH_HOME 真装一遍），别因为本地 junction 还能用就以为没事。
- **包名是单一事实源**：改名（例如为发布改 scope）时 `package.json.name` / `cordis.patch.yml` / 预设插件行必须同改；smoke 有断言钉住三处。
- **`ctx.effect(cb)` = 立即执行 cb + 用返回值当 disposer**（真库探针实测，见 docs/01 决策 12）：凡"注册即副作用"这样写；凡"清理逻辑"必须**包在返回的函数里**。
  写反的后果不是报错而是**静默失效**（路由 refcount 就这么失效了很久）。
- **假对象必须复刻真契约**：smoke 的假 ctx 曾把 `effect` 语义写反，于是"清理体写在 cb 里"的真 bug 在测试里看起来是对的。
  **测试替身的契约错了，测试就在替 bug 背书**——契约可疑时，先用真库写一个最小探针（本轮就是这么定位的）。

## 发布-同步纪律（两种模式：日常本地迭代 / 发版同步）

- **日常迭代 = `node scripts/release-sync.mjs --local`**（`npm run sync -- --local`）：**不发 GitHub**。原子完成
  build → pack（带构建戳）→ **跳过上传** → 同一 tgz 部署本机安装根（`D:\plugins\package`）→ 用**本地 tgz 的 `file:` 规格**
  把同一份字节装进 profile（挂载源 = 本地构建产物）→ 终验"**挂载副本 == 刚构建的字节**"（逐文件 sha256）→ 写 `.sync-state.json`。
  - 构件落在 `D:\plugins\_artifacts\<资产名>.tgz`，**必须是稳定目录而不是 tmpdir**：这个路径就是 profile 的依赖规格，
    放临时目录的话系统清理后该 profile 的 `pnpm install` 会在**下一次**安装时莫名失败（离本次构建很远，极难归因）。旧构件每次自动清理，只留当前那一个。
  - **为什么用 `file:` 而不是切回 junction/preset 装法**：junction 会**新增一条挂载路径**——"我改的是哪份代码"于是有两种答案，
    答错**不报错**。`file:` 仍然只有一条路径（profile bundle 行），只把"从哪取字节"从远端资产换成本地 tgz。
    机制由 `npm run test:bundle` 自证（同版本号、不同路径的 tgz ⇒ 装到的就是新字节）。
  - **⓪ 落后检查**：跑之前先 `git fetch` 比对 `HEAD` 与 `origin/<branch>`，落后 >0 个提交就**直接失败**（`--allow-behind` 绕过）。
    理由：**"本地永不落后于 GitHub"不会自动成立**——有人在 GitHub 上直接改、或换机器提交，本地就落在后面，
    而"在最新版本上迭代"这个前提破了以后**没有任何症状**，直到发版时才发现分叉。离线（fetch 失败）明确标注"未能确认"并继续。
- **发版 = `node scripts/release-sync.mjs`**（不带 `--local`）：build → pack → sha256 比对/上传（`--clobber`，幂等）→ 同一 tgz 部署本机安装根
  → 按 **GitHub 资产 URL** 重装 profile → 终验 sha256 三向一致 → 写 `.sync-state.json`。**发版把本机与 GitHub 拉回同源。**
- **`.sync-state.json` 的 `mode` 字段区分两种状态**（`local` / `release`）：本地模式下 `remoteSha` 保留**上一次发版**的值并记 `lastReleaseAt`——
  **绝不把"未上传"伪装成"已同步"**。这是本地模式唯一新增的风险，必须让它可读。
- **回退到 GitHub 版本**：`dsh plugin --profile web add <Releases 页面的资产 URL>`（发版模式做的就是这件事）。
- 两种模式都**需要重启 `dsh web` 才生效**（profile bundle 挂载不热更）。本机安装包由当次构建用的**同一个 tgz** 解压而来，部署副本与挂载副本逐文件同源。
- **挂载模式（决定"谁看得见工具/skills"）与 `--local`（决定"从哪取字节"）是两件事，正交**：
  bundle 行 = 该 profile **所有会话**可见（含官方标准预设）；**预设行 + junction = 仅「PPT 工作室」预设可见**。
  想要会话级隔离就切后者（`dsh plugin --profile web remove <包>` → `node scripts/install.mjs` → 重启；README §10 有切换与回退命令），
  日常迭代照旧 `--local`——它现在**两种挂载模式都自证**（非 bundle 走"穿过 junction 读到的字节"）。
  插件**无法**在 bundle 挂载下自己按预设过滤：注册发生在插件 `apply`（profile 级），要按预设隔离就得从预设组合里注册。
- 版本号：未获用户指示不改（当前 **1.1.0**；历史值见 docs/03）；**资产名带构建时间 + 构建戳**（2026-09-15 起）：`dsh-ppt-studio-<版本>-<YYYYMMDD-HHmm>-<sha256 前 8 位>.tgz`。
  > 2026-09-18 改名说明：包名由 `@dsh-external/dsh-ppt-studio` 改为**无 scope** 的 `dsh-ppt-studio`（发布到 npm），
  > 于是 `npm pack` 产出的资产名也从 `dsh-external-dsh-ppt-studio-…` 变成 `dsh-ppt-studio-…`；v1.0.2 及更早的资产仍在 Releases 页上（老用户重装不受影响）。
  **时间段的用处**：老资产**不删**（已装用户靠它重装），页面上会并排多条名字近似者，sha 段看不出新旧 ⇒ 取时间最新那条即当前版本；发布日志里同时打印本轮的完整资产名。
  原因（本轮实测）：用 `--clobber` 覆盖**同一 URL** 的内容后，**`dsh plugin add <同一 URL>` 不会重新下载**
  （pnpm 按 URL 规格复用旧副本，`--force` 也没绕过；独立 GET 证明 URL 侧已是新字节 ⇒ 复用发生在包管理器侧）
  ⇒ 用户"重跑同一条命令升级"会拿到旧版本。换名 ⇒ URL 必变 ⇒ 必然重取。因此**取消"同 tag 资产原地更新"这条口径**：
  每次构建产出新资产名，旧资产保留（历史可回溯）。

### npm 公共通道（2026-09-26 起：Trusted Publishing / OIDC，全自动）

- **一次性人工前提**（只有这一次要动手）：npmjs.com → 本包 → Settings → **Trusted publishing** → Add trusted publisher → GitHub Actions：
  `Organization or user = zbsph` ｜ `Repository = dsh-ppt-studio` ｜ `Workflow filename = publish.yml`（只填文件名、区分大小写、必须与 `.github/workflows/publish.yml` 一致）｜ `Environment name` 留空 ｜
  **Allowed actions 必须勾上 `npm publish`**（全自动档；只给 stage 权限时 CI 会以 `E_STAGE_REQUIRED` 失败）。
  官方两条硬约束：① 保存时**不校验**，字段错只在首次发布时以 `ENEEDAUTH` 暴露；② 已建立的连接**不可编辑**，要改只能删除后重建。
  命令行等效（仍会要求浏览器 2FA）：`npm trust github dsh-ppt-studio --repo zbsph/dsh-ppt-studio --file publish.yml --allow-publish`。
- **之后每次发版零手工**：`.github/workflows/publish.yml` 由 `release: published` 触发 → 等 Release 资产出现（≤15 分钟——资产的 `gh release upload` 在 `npm run sync` 里，**晚于**该事件）→ **按上传时间取最新那条 tgz**（同一 tag 上可能有历次重建，与 README §1.2 同一口径；**不二次打包**，保住"两条通道同一份字节"）→ OIDC `npm publish` → 发后自证 `registry dist.integrity == 本地 tgz 的 sha512`。
- **触发顺序陷阱（务必记住）**：`gh release create` 早于资产上传，所以**不能**写成"事件触发 + 立刻在 CI 里打包"。本工作流用"等资产"把顺序问题变成可控等待；替代方案是先建 draft、`npm run sync` 之后再 `gh release edit --draft=false`（GitHub 官方：draft 被 publish 时 `published` 事件会触发）。
- **手动补发 / 重发**：Actions → *Publish to npm* → *Run workflow*（填 tag）。
- **为什么不在 CI 里重新打包**：同一份源码在 CI 里打包会因文件时间戳与命名差异产出**不同字节**，直接破坏"registry 字节 == Release 资产字节"这条不变量；smoke §51 有断言禁止二次打包。
- **为什么第 ④ 步不再需要人工批准**（2026-09-26 用户拍板）：OIDC + `npm publish` 是"零长期凭据"的自动发布通道；代价是放弃"每次上线必须本人 2FA"。若要恢复人工闸门：把信任关系权限收窄为 stage，并把工作流改成先 stage、再人工批准——npm 官方明确 `npm stage approve` **不能**用 OIDC 完成，必须交互式 2FA。
- **安全加固（按官方 migration tip 的顺序）**：① 先让这条通道真跑通一次；② 再到本包 Settings → Publishing access 选 "Require two-factor authentication and disallow tokens" → Update Package Settings（官方明文：这条**不影响** trusted publisher）；③ 然后删除不再需要的长期 token。
- **能力边界**：仅支持云托管 runner（self-hosted 不支持）；`npm whoami` 不反映 OIDC 状态；OIDC 只能跑 `npm publish` / `npm stage publish`，其它 stage 子命令与 `install`/`view`/`access` 仍需传统认证；npm CLI ≥ 11.5.1（OIDC）/ ≥ 11.15.0（stage 命令）、Node ≥ 22.14.0 ⇒ 工作流用 node 24 并带版本门禁。

## 宿主升级纪律（DSH 换版本时必做，2026-09-12 起）

- **先确认版本再动手**：`dsh --version` + `npm view @deepseek-ai/dsh dist-tags`（`latest` 与 `next` 可能不同；本机基线写进 README §0.1 与 package.json 的 peer 范围）。
- **契约逐项核对，不靠记忆**：对本机活进程用 Inspect 取权威签名——`Service.listService`（`tools` / `commands` / `systemPrompt` / `webServer` / `skills` / `agent*`）与 `Event.listEvents`（`session/event` / `system-prompt/assemble`）。**服务名与事件载荷都可能变**（本轮实例：DSH 只有 `agents` 服务，`agent` 服务并不存在）。
- **会话身份只走官方通道**：工具内 = `execute(args, exec)` 的 `exec.agent`；waterfall/命令内 = `context.agent` / `invocation.agent`。禁止 `ctx.get('agent')`。
- **升级后必须"真进程验证"，不能只跑单测**：临时覆盖层（`dsh --profile headless --patch <overlay.yml> "<任务>"`）+ 落盘探针，实测三件事——① 插件 host 装配成功且工具可调；② 内嵌 skill 在技能注册表里可见（`ppt_state.manualSkill.visible`）；③ `system-prompt/assemble` 里确实出现 `ppt-workflow` 段（探针计数，别问模型"你看到没有"——模型自述不可信）。
- 覆盖层与探针文件属临时物，验证完立即删除；headless profile 的 junction 用 `cmd /c rmdir` 删（`Remove-Item -Recurse` 有跟随重解析点删目标内容的风险）。
- **绝不对可能含 junction 的目录做 `Remove-Item -Recurse`（2026-09-14 事故，已修复）**：
  本机 `~/.dsh/profiles/web/node_modules/yaml` 与 `D:\plugins\package\node_modules\yaml` 都是 junction，
  而 PowerShell 5.1 的 `Remove-Item -Recurse` **会跟随重解析点**。事故链条：临时对照包被 `install.mjs` 链上
  `node_modules/yaml`（指向 dsh 安装内的 yaml）→ 随后 `Remove-Item -Recurse` 该临时目录 →
  **把 `@deepseek-ai/dsh/node_modules/yaml` 的内容清空**（目录还在、包没了）→ dsh 整棵插件树加载失败
  （`dsh-settings-file` / `dsh-credentials-local` 找不到 `yaml`）。
  修复：从本机同版本副本（`~/.dsh/profiles/web/node_modules/yaml`，yaml@2.9.1，满足 `^2.9.0` 与 `^2.4.2`）**普通复制**回
  `@deepseek-ai/dsh/node_modules/yaml`，用 `dsh --version` + `dsh --profile headless --help` 验证插件树恢复。
  规矩：① 删任何目录前先 `cmd /c rmdir <里面的 junction 子目录>`；② 临时包用 `cmd /c rmdir /s /q` 或 Node `fs.rmSync`（不跟随重解析点）；
  ③ **造对照包一律用普通复制（`Copy-Item`）并自带 `node_modules/yaml`，不要用 `install.mjs`**（它会建 junction）；
  ④ 指向宿主的链接用完立刻删。
- **预设也要比对（2026-09-12 血案）**：`agent-presets/ppt/agent.cordis.yml` 是**随包 standard 预设的全量副本 + 本插件人格**，宿主的预设配置会随版本漂移（实例：0.1.5-rc.2 把 dsh-persona 的 `text` 改成 `prefix`+`suffix`，副本没跟 → 一切换预设就弹 `$.prefix missing required value`，单测与工具契约核对都发现不了）。每轮升级后跑 `node scripts/check-preset.mjs`（`npm run test:preset`），有漂移即修。
  - **2026-09-24：参照物的位置和格式都变过，脚本必须都认**。0.1.6- 是 `dsh-agent-presets/presets/standard/agent.cordis.yml`（条目数组）；0.1.7+ 是 `dsh-web-app/presets/standard.patch.yml` 的 `insert → config.plugins`。脚本按文档形状自动识别并**在输出里写明认到哪种**；`--ref <文件>` 可钉住参照（本机装了 DSH 时无法制造"找不到参照"的场景，测试靠它）。
  - **不许静默跳过**：0.1.7 升级当天的实际教训是——脚本找不到旧路径就打印一行跳过、退出码 0，于是 `npm test` 报 250/0 全绿，而**整套 DSH 相关检查其实一条都没跑**（本轮真问题恰恰是"预设永远不会出现"）。现在找不到参照会醒目告警，`--require`（发布/干净安装门禁用）直接失败。
- **跨层验证（2026-09-14 连线方向血案）**：同一份内容有三层产物——HTML 预览（render-html.js）、OOXML 成品（export-pptx.js）、真渲染图（Office/Edge）。**任何一层单独通过都不算过**：实测出现过"预览全对、PowerPoint 里斜线镜像/× 少一笔"（`straightConnector1` 丢 `flipH`/`flipV`）。规矩：凡新增/修改元素类型的导出编码，必须 ① 加**从产物反推的自证断言**（如 `connectorEndsFromXml` 端点比对进 `report.parity`）② 至少一页 `ppt_visual` 真渲染人眼复核。

## 内置技能的增改纪律（2026-09-14 起）

技能是**内容**，不是代码——它会直接影响模型行为，且用户看不到 diff。因此按以下规矩增改：

0. **禁令准入（借 ppt-master 的 prompt-style 判据，2026-09-14 引入）**：手册里每一条"禁止/必须/配额"都必须能说出**让它变硬的机制**
   （`ppt_verify` 的哪条断言、导出器行为、格式限制、门禁顺序、读入成本）；说不出机制的 → **降级为"经验值（可覆盖）"或删掉**。
   这条是防止手册越写越僵、越写越像说教的唯一闸门。配套两条：
   - **单一所有者 + 指针**：同一规则只在一处写全，别处只写"见 §N / 见某工具"；复述即产生第二所有者，两边必然漂移。
   - **标签强度分级**：用 `**硬规则**` / `**默认（可覆盖）**` / `**参考·非约束**` 把"必须"和"建议"在字面上分开——
     模型把风格建议当硬规则执行，正是我们出过事故的样子。
   - 反向红线：**绝不把别家 skill 里的具体数值当默认基线抄进来**（它们的"Default — X"读起来像推荐默认值，抄进来同时违反第 2 条并让插件变差）。
0a. **外部经验值的两道闸（2026-09-14 用户抓到的失误，务必照做）**：从外部 skill / 文章吸收任何经验值前必须过两关——
   ① **机制闸**：这条能说出机制吗？说不出 → 不进手册（顶多写成"参考"）。
   ② **原则闸**：它与我方既有门禁 / 原则冲突吗？冲突 → **一律不进**，哪怕它在别处是主流做法。
   失误实例：从 ppt-master / 归藏的调研报告里抄了"同一明暗基调连续 3 页以上就该换"，它**说不出机制**，
   而且与 `theme-conformance`（颜色必须出自 theme）和"模板基调统一"直接冲突——会把模型推向"中途换底色"这种更差的结果。
   已删除，并把正确口径写成"**节奏靠密度与构图，不靠改底色**；深/浅切换只跟随模板或用户既有的分区设计"；
   同时加了一条 smoke 防线（劝人改全册底色/主色 = 违规），校准：5 条植入违规全抓、6 条合法表述零误报。
0b. **不吸收第二套门禁**：外部 skill 的校验脚本/自检命令/配额表一律不搬——我们只有 `ppt_verify` 一套门禁语义；外部能做而我们不能做的（联网、生图、HTML 运行时）不写进手册。
0c. **手册里的"事实"是第二类风险，与经验值分开管（2026-09-14 全面自检新增）**：0a/0b 管"该不该说"，
    这里管"说得对不对"——手册写错一个工具名/字段形状/错误码/严重度标记，模型就会照着错一次（而且看不出来）。
    规矩：**手册里的每个事实都要能指回源码行**——工具名 → 注册表；DSL 形状 → `pptd/schema.js` 的校验器；
    错误码与严重度 → `verify.js`；预览/交付行为 → 渲染器与导出器；阈值 → 那个常量本身。
    本轮自检抓到的 6 类实例：① `chart` 的 `data` 形状写成 `[{label, value}]`（schema 只认 `{cols, rows}`，照写必被拒）；
    ② 三本手册把 warning 标记写成 `[⚠]`（`ppt_verify` 主清单实际是 `[~]`）；③ `density`/`near-align` 被归到 `[·]` 建议（实际 `[~]` 警告）；
    ④ 手册门禁清单漏了**默认就开**的 `theme-conformance`；⑤ "预览里图表带分类名"对 pie 不成立（pie 连分类名都不画）；
    ⑥ 6 处 "smoke 181 断言" 只能靠人工同步。
    已落成 **13 条机器断言**（smoke §37/§38，套件 181 → 194）：`ppt_*` 工具名存在 / 门禁错误码集合与源码一致 / 每个错误码都写进手册 /
    手册门禁清单里的 code 名真实存在 / 警告标记是 `[~]` 而非 `[⚠]` / `density`·`near-align` 不得归到 `[·]` / chart 的 `data` 形状 /
    预览截断阈值与 `svgCharts.js` 一致 / `/ppt` 子命令存在 / 讲稿章节写明"不导出备注" / 缩字下限常量与导出器一致 /
    `SCHEMA_REF` 自洽（不得声称 decoration 豁免出界）/ **引用计数自证**（文档里的 "smoke N 断言 / N/N" 必须等于本次真实断言数——
    这条实现当轮先红后绿，一次点出 6 处过期引用，是治"加断言忘了同步文档"这个反复疏漏的根）。
    同时清理掉的同类问题：`非对称是默认`（把设计偏好写成默认，会跟用户的对称模板打架）、`约三成面积的低细节区`
    与"3–5 条讲稿要点"（裸经验值未打"经验值（可覆盖）"标签）、"宁可拆两页"（与"页数由用户定"冲突）。
0d. **产物必须用真消费者验（2026-09-14 血案）**：加备注页时先写了 `<p:notesMasterIdLst>`——**python-pptx 照读不误，真 PowerPoint 直接报"文件或目录损坏"（0x80070570）**。
    第三方库通过 ≠ 能打开。凡改**导出编码/OOXML 结构**，必须至少走一次真消费者（真 PowerPoint `ppt_visual` / 真浏览器 `ppt_shot`），
    自证断言（parity）只证明"我写出去的和我以为的一致"，不证明"别人能读"。定位手段：以**已知能打开的同类原生文件**为底做**减量二分**
    （逐个撤掉自己新增的部件/元素，看撤掉哪一个是它开不了的），比读规范猜快得多、也可靠得多。
0e. **触发面纪律：技能描述里的触发条件，不许对"正在干活的模型"恒真（2026-09-15 用户反馈）**：
    症状：PPT 任务**开工时**模型先加载了答疑手册 `ppt-studio-manual`——它的描述写着"如何开始 / DSL 语法速查"，`whenToUse` 写着
    "**或模型不确定某一 DSL 写法、工具语义、交付路径时**"。后半句对正在做 PPT 的模型**永远成立**，于是每轮任务白付一次几千字符成本，
    而正文讲的是"怎么回答用户提问"。这不是模型不守规矩，是描述把"自触发条件"写成了触发条件。
    三查规矩：① **问答类技能**只由"用户提问"触发，并显式写出否定句（"制作任务进行中不要加载"）；② **工作类技能**由具体工作面触发（定纲/放图表/写文案）；
    ③ 禁止"不确定时 / 拿不准时 / 需要时"这类**恒真或半恒真**触发语——模型在干活时永远"可能需要"。替代写法：在描述里直接给出**权威来源**
    （"写法不确定 → 调 `ppt_schema`/`ppt_check` 拿输出，不要读手册"）。机器防线：smoke §42 三条（描述与 whenToUse 的问答触发 + 否定句、
    正文开头横幅、制作三本正文零指向答疑手册）；`audit-manual-facts.mjs` 两条证据检查。**另一条同源教训**：交叉引用也是触发面——
    制作手册正文里写一句"详见 `ppt-studio-manual` §5"，工作期读到就会把模型引去加载答疑手册（本轮已清掉）。
1. **只增不改**：工作流提示词由 `scripts/fixtures/workflow-baseline.json` 做**逐行超集**断言（`npm test` 里两条"★老用户不受影响"）。新增指引＝加一行；**任何对旧行的改写或删除都必须先经用户确认**，确认后跑 `node scripts/dump-workflow-baseline.mjs` 重建基线（不确认就别重建——重建会让护栏失效）。
   重建后**必须逐行审查 diff**：本轮（2026-09-14，用户确认修 `router.js` 括注错位）相对 HEAD 只有两类变化——
   5 条"改后的溢出行" + 5 条**此前漏进基线的技能指引行**（纯增行不会被超集断言发现，所以基线里的"新增行"也要靠重建补齐）。任何第三类变化都要停下来查。
2. **不许写死数值**：技能正文不得出现"默认 12pt""必须 ≤8 页""每页 ≤40 字"这类**规范性数值**。smoke 有 5 条校准过的正则做机器防线（8 条植入违规全抓、8 条合法表述零误报）。经验值一律写成"经验值（可覆盖）"，并把优先级写成"用户指令 > 手册 > 工具默认"。
2b. **自检条目要可核对**：自检章节的每条都应能"数出来或对照某个工具输出"（存在性/计数/一致性），不写"是否美观""是否清晰"这类无法核对的话
   （借归藏 checklist 的"现象→做法→机械自检"形状；P0 项必须先清零）。
   > **这道守卫的诚实边界**：正则只能抓"规范性措辞 + 数值"这一形状，**抓不到**"裸阈值当建议写"（如"列 ≤5、行 ≤7 才好读"）、也抓不到语义偏移（把"逐元素手工声明"写成"站在带上就声明"）、不可执行的指令（要求 table 右对齐）与三本之间的重复。所以 `docs/06 §7.4` 的**独立评审**是必需的第二步：新写或大改技能后，交一个独立 agent 逐条对照源码评审，把缺陷清单落进 docs/03。
   > **2026-09-14 补充**：smoke §37 之后，"工具名 / 错误码 / 严重度标记与分级 / DSL 形状 / 预览阈值 / 引用计数"这几类**已进机器防线**（对照源码，不靠人眼）；仍然只能靠独立评审的是：裸阈值当建议写、语义偏移、不可执行指令、跨本重复——所以 §7.4 那一步不能省。
3. **每本自包含且短**：描述 ≤500 字符且**只写触发**（描述会常驻系统提示，正文按需加载）；正文几千字符量级；不放脚本、不依赖外部文件。新增一本＝新建 `skills/<kebab-name>/SKILL.md`，`install.mjs` 与 `lib/skill.js` 自动纳入（无需改代码）。
4. **不与用户自装技能抢位置**：一律 `ppt-studio-*` 前缀；通用能力（去 AI 味、润色）写"优先用用户已装的同类技能，本手册兜底"，不复制别人的内容。
5. **改动要有前后对照**：技能效果属"软收益"，必须用 A/B 评测（同一 brief、同模型、同装配，门禁分数 + 信号扫描）落到 docs/03/04；不做"感觉更好了"的结论。

## 文档文风范围（2026-09-18 用户拍板）

"去 AI 味 / 面向用户重写"这类**文风**改动，只做在**仅给用户看**的文件上：

- **要改**：`README.md`（GitHub 仓库页 / 包页）、GitHub Release 说明。用户真的会读它们。
- **不要改**：`skills/*/SKILL.md`（模型运行时读）、`docs/*.md`（开发与决策档案）、`agent-presets/**`（persona 提示词）、代码注释。
  这些是给模型和开发看的，**信息密度与精确性优先**；重写文风只会增加破坏机器断言的风险（4 本手册被 `audit:facts` 的 39 条与
  smoke 的多条断言钉着，2026-09-18 实测：一次"顺手润色"就踩红了两条）。
- 判据一句话：**问"这份文件是给谁读的"**。只给用户读 → 可以重写文风；同时给模型或开发读 → 只做**事实更正**，不动文风。
- 两边都需要的同一内容 → **写两版**（用户版放 README，权威版放 docs 或技能），不要用一份文件同时满足两类读者。
- 边界案例：技能手册的内容会影响用户最终看到的话（模型照它回答），但**文件本身不是用户读物** ⇒ 按本条**不改文风**；
  要改的是它的事实准确性（走上面的 §0c 事实链与 `audit:facts` 断言）。
- 文风改动的验收方式：`npm test` 的"文档计数自证"必须仍绿（README 里引用的 smoke 断言数要与真实数一致），
  且改后**事实零变化**——命令、路径、版本、断言数、FAQ 里历轮反馈的事实一条都不能少。

## 禁止事项（保护性底线）

- 不删标准预设任何行（预设 = standard 全量 + 插件行）。
- 不把任何 ERROR 降级为 warning（严格性只升不降；降 = 必须用户确认 + 更新 01 文档）。
- 不静默切换引擎（auto 语义 = pptd；切换必须显式或用户确认）。
- 不做无视用户指令的自动缩字（下限 = 用户指令 theme.minFontSize；未设仅 60% 原字号防荒谬保底，绝不升字）。
- 不引入新的运行时 npm 依赖（yaml 是唯一例外；新增须论证）。
- **不拿"能跑通"当"没问题"**：凡"机制应当生效"的断言（提示词注入、技能交付、会话状态、路由判据），必须有**可观测证据**（探针计数 / 注册表查询 / 状态文件），否则记为"未验证"。
