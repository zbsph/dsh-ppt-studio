## 2. 每个族的交付定义（DoD）

1. **布局策略**：写在该族的 `layout()` 里，只做几何；取色/字号/线宽/间距**全部来自样式令牌**（族没有审美）。
2. **契约夹具**：进 `scripts/verify-diagram-ir.mjs` 的族用例表（确定性 / schema 合法 / 落在画布内 / attach 端点落边）。
3. **真渲染验收**：导出 + PowerPoint COM 出图 + **读图确认**（人眼过一遍"像不像这个族"）。
4. **组级/页面级审阅**：`npm run render:group` 出组级裁剪图；整页图由 `ppt_render` 出。
5. **`maturity`**：初版一律 `beta`；连续两轮真渲染无问题后升 `stable`。
6. **优雅降级**：空间不足/结构不合法 ⇒ 省略装饰并记 `notes`，或整体不产元素；**绝不产半成品**。

### 5.8 绘制规则（**设计阶段敲定**，2026-09-28 用户提出并确认）

这几条是"什么地方能用什么画法"的硬规则，写在引擎里、也用自证脚本守住：

| # | 规则 | 为什么 | 落实处 |
|---|---|---|---|
| R1 | **折线永远轴对齐**（正交路由）；斜段只能出现在"环/放射"语义里 | 正交是这套图的工程感来源；也是"竖/横段 AABB 宽或高为 0 ⇒ 不触发重叠判定"这条前提的基础。斜段还会让**箭头方向不确定** | `orthogonalize()`，`makeEdge` 默认开启；`cycle` 的外环弦用 `orthogonal: false` **显式豁免**（funnel 的斜边是 custGeom 形状，不是折线） |
| R2 | **箭头端紧邻的一段必须 ≥ 18px 直线**，拐点不得贴着箭头 | 拐点贴箭头时，箭头三角"吃掉"整段 ⇒ 看起来像断的、看不出指向（用户实测附图） | `arrowEndRuns()`；顺序 = 正交化 → 保证直段 → 再正交化收口 |
| R3 | **后处理只准挪拐点、不准动端点** | 端点承载 `attach` 语义与"箭头必然落边"的判定 | `arrowEndRuns()` 只改 `p[n-2]`/`p[1]` |
| R4 | 文字标签**框紧贴文字**，标签与图形的间距由**常量**决定 | "离太远/时远时近"是用户实测反馈；能写成常量的就不该留给目检 | steps：框宽=估宽+8，框内缘距圆点边固定 12px |
| R5 | 承载语义的背景图形用 `role: decoration`（完全豁免重叠），不要靠"声明重叠"掩盖 | 跨带连线必然穿过"节点所在的带"，靠 contains 豁免不了（layers 实测） | swimlane 车道、layers 分组带、steps 引导环 |

> 教训留档：R2 的第一版实现（沿最后一段挪拐点）**把前一段拉斜**了 ⇒ 才逼出 R1。
> 两条规则必须**成对**实现：`orthogonalize(arrowEndRuns(orthogonalize(pts), arrow))`。

### R10 人工审图模式：撞门禁的产物**一并交用户裁定**（用户要求，2026-09-30）

当用户**明确表示要人工审图**时：

- 撞门禁（红）的产物**不得静默丢弃**——连同"卡在哪条断言、具体数值"一起交用户看，由用户裁定是**图的问题**还是**门禁过紧**；
- 交图时必须给出三件事：**这版过了哪些门禁 / 卡在哪条（含数值）/ 我的判断与代价**（例："返工边方向可读性更好，但密集合成夹具多 1 处真交叉"）；
- 用户裁定"门禁过紧"时，放宽门禁必须**同时**给出反例，证明放宽后仍能抓到真缺陷；裁定"图的问题"时才回退或改画法；
- 纪律仍然有效的是"**不留半成品提交**"，但**不等于**"红就删掉、连图都不给用户看"——这两件事我此前混为一谈了。

理由：门禁是工具不是目的；**观感是否正确，用户才是最终裁判**，我不能用门禁替用户做观感决定。



**不要**用"几何禁止项"去表达（踩过两次：一次把共用竖管判成缺陷，一次把"中点进出/合并分叉"判成缺陷）。用户给的正例图里同时存在下列画法，**它们都是标准画法**：

- **中点进出**：干线对齐节点边的中点竖直进入（箭头朝上/朝下）✓ —— 这是最标准的画法，**不是**"末段与中线共线"的缺陷；
- **合并后分叉（T 形结点）**：两条返工路径共用一段干线，在**远离节点**的结点处分叉 ✓ —— 与 R7 的"共用干线"同源；
- **共线但不重叠**：两条线共点/共线而区间不相交 ✓（已有 `line-collinear-overlap` 只报"共线**且部分重合**"）。

真正算缺陷的只有一种：**同一条节点边、同一个点上"一条进 + 一条出"** ⇒ 两条边连成一条直线**贯穿节点**，读者会把它读成一条线（实测：图 10 的"评审不合格"边从 `已成样` 左边出发，而 `烘焙毕` 的箭头正落在同一点 ⇒ 完全读不出"返工"）。
修法与验证：

1. 该边的**进出点要错开**（换一条边进出，或沿边平移 ≥8px），或在**远离节点处**分叉；
2. 修完必须**双向验收**：① 视觉上目标框处有明显箭头、方向可读；② `verify:route` 的密集夹具（多回边）**不因新走法压盒/交叉**；两边都过才算修好（只满足一边即视为未修好，回退）。
