# 12 · 阶段 B 设计说明：图编译核心（IR + 布局引擎 + 样式档案 + 物化）

> 依据 docs/07 §5（阶段 B：IR + 布局框架 + 样式档案 + 物化为现有元素 + 预览↔成品**同源** + 结构关系自动产出 + 组级裁剪渲染）。
> 本文件是阶段 B 的实施契约：**先钉契约，再写代码**；每条决定都标注"推荐默认（可推翻）"。

## 1. 目标与非目标

**目标**：让"复杂图"从**手写像素**变成**写结构**——用户给节点/关系/层次，引擎算几何、产出结构关系、并保证成品里不出结构错误。

**非目标**（本阶段不做）：
- 不做"审美决策"（配色/风格由 `$theme` 或参考稿档案决定；引擎**自身没有审美**）；
- 不做图族全家桶（阶段 C；阶段 B 只做 2 个族来验证引擎：`flow`、`layers`）；
- 不做参考稿结构反推（阶段 D 的北极星）；
- 不引入任何运行时依赖（仍是 `node:*` + 自研）。

## 2. IR 语法（页面级 `diagram:` 块，推荐默认）

```yaml
diagram:
  type: flow            # flow | layers（阶段 C 扩充：tree/matrix/timeline/cycle/swimlane/…）
  direction: LR         # LR | TB（flow 用）
  title: 数据链路        # 可选：图上方的标题
  nodes:
    - {id: n1, label: 采集, emphasis: primary}     # emphasis: primary|accent|plain（只影响取色，不影响几何）
    - {id: n2, label: 清洗}
    - {id: n3, label: 计算}
  edges:
    - {from: n1, to: n2, label: 实时}               # label 可选（放在连线中点上方）
    - {from: n2, to: n3, style: dashed}            # style: solid|dashed（映射到 line.dash）
  groups:
    - {id: stage1, label: 第一段, members: [n1, n2]}  # 可选：分区/泳道（产出 contains + groups）
  bounds: [60, 120, 840, 300]                      # 可选：给图的画布区（缺省用安全区内接矩形）
  style: $theme                                    # 可选：$theme（默认）| <参考稿档案 id>（阶段 D）
```

- **id 必须是页面内唯一**（与元素 id 同一命名空间；引擎会加前缀，见 §5）。
- `focus`/`maxNodes` 等规模控制留给阶段 C 的族策略。

## 3. 布局引擎契约（`src/pptd/diagram-ir.js`）

```js
validateDiagram(diagram, {file})            // → errors[]（结构校验；错误信息带 file 前缀，与 schema 一致）
styleProfileFrom(theme)                     // → 样式令牌（间距基数/节点尺寸/字号/线宽/圆角/取色序列）
layoutDiagram(diagram, {bounds, style, measure, idPrefix})  // → { elements, groups, notes, stats }
```

**硬契约**（会被自证脚本逐条断言）：
1. **纯函数**：不修改输入；同输入两次输出**深度相等**（确定性）；
2. **不改既有路径**：页面上没有 `diagram` 时，本模块**不被调用**，元素列表与从前逐字节一致；
3. **只产出既有元素类型**（`shape`/`text`/`line`），**不新增元素类型**；
4. **不产出结构冲突**：产出的元素之间除"有意重叠"外不得相交（节点不叠、标签落在节点内、连线落在节点之间的间隙）；
5. **自动产出结构关系**（见 §6）——几何与关系由同一个引擎产出，因此天然自洽；
6. **不支持的 `type`/字段 ⇒ 优雅降级**：`elements: []` + `notes[]` 说明，**绝不产出半成品图**。

## 4. 样式档案（style profile）

| 令牌 | 来源（推荐默认） | 用途 |
|---|---|---|
| `gapX/gapY` | theme `spacing.base`（缺省 24）派生 | 节点间距、边距 |
| `nodeW/nodeH` | 由画布与节点数推算（有下限/上限） | 节点尺寸 |
| `fontSize` | theme `textStyles.body.fontSize` 的 0.9–1.0 倍 | 节点标签 |
| `lineWidth` | theme `line.width`（缺省 1） | 连线/边框 |
| `radius` | theme `radius`（缺省 8） | 圆角 |
| `palette` | theme `colors` 的**有序**取色序列（primary → accent → soft…） | `emphasis` 取色 |

**铁律**：引擎只在令牌里取色/取尺寸，**不硬编码颜色**；主题换色后图跟着换（阶段 D 的参考稿档案只是另一份令牌）。

## 5. 物化契约（怎么接进现有链路）

- 展开点在 **`resolveDeck`**（`src/pptd/schema.js`）：`validatePage` 通过后，若页面有 `diagram` ⇒ 调 `layoutDiagram`，把产出的元素**追加**到 `page.page.elements`，把产出的 `groups` 合并进 `page.page.groups`。
- 因此 **`normalizePage` / `render-html` / `export-pptx` / `verify` 全部零改动**——它们继续吃"普通元素 + 结构声明"，预览与成品**天然同源**（同一份归一化元素）。
- **id 前缀**：产出的 id 一律带 `d<序号>_` 前缀（如 `d1_n1`），避免与手写元素撞名；`groups`/`contains`/`attach` 里的引用同步加前缀。
- 页面可以**既有 `diagram` 又有手写 element**（缝合页）：两者共享同一命名空间与安全区校验。

## 6. 结构关系自动产出（阶段 A 的地基在这里被"用起来"）

| 关系 | 谁产出 | 说明 |
|---|---|---|
| `groups[]` | IR 的 `groups` | id 加前缀；成员 = 节点 id（含嵌套时按 IR 层次） |
| `element.contains[]` | 每个 `groups` 条目产出一个**容器 shape**，声明包含其成员 | 容器是几何真实的（包住成员，pad ≥ 6），因此几何反验证必然通过 |
| `element.attach{from,to}` | 每条 `edges` 产出一条 line，两端锚到节点边 | 方向决定 `side`（LR：右→左；TB：下→上）；因此**箭头必然落边**（阶段 A 的 `arrow-not-on-edge` 永不触发） |
| `expectedOverlaps` | 仅当引擎确实产出有意重叠时（本阶段：无） | 引擎不靠声明掩盖自身几何问题 |

**这条是阶段 B 的核心收益**：结构关系不再是"用户手写 + 引擎事后验证"，而是"引擎产出 + 用户可改"。

## 7. 组级裁剪渲染（隔离看图）

- 目的：整页缩略图会掩盖小尺寸缺陷（docs/07 R21）。做法：给定"页面 + 一个 group（或元素 id 列表）"，只渲染该组的包围盒（外扩 `pad`），输出独立 PNG/HTML。
- 接口（推荐默认）：`ppt_render` 增参 `group=<groupId>`（局部渲染，与 `pages=` 同类），CLI 侧 `scripts/render-group.mjs` 先行验证；报告里必须写明"这是第 N 页的某个组合（bbox …），不是整页"。
- 与门禁的关系：组级渲染是**审阅材料**，不改变 `ppt_verify` 的判定；`ppt_verify` 仍只出整册/局部页门禁。

## 8. 硬门槛与回归门（沿用阶段 A 的四条 + 阶段 B 专属）

1. **确定性**：同一 deck 两次导出除 `core.xml` 时间戳外逐部件一致（含 IR 展开的 id 编号）；
2. **性能**：150 元素基线不退化（`scripts/bench-diagram-scale.mjs`）；新增"含 IR 的 150 节点页"基线（阶段 C 用）；
3. **判据严格性**：IR 校验与布局不变量的负面对照必须报红（自证脚本）；
4. **prompt 增幅 ≤5%**：`npm run probe:prompt:check`（阶段 B 若新增工具/参数必须复测）；
5. **无图页产物逐字节不变**：无 `diagram` 的页沿用阶段 A 的门控（`usesStructure`）与基线 tag 对照；
6. **预览↔成品同源**：由 §5 的结构保证（零改动）——自证脚本断言"预览 layout.json 的元素 == 导出消费的元素"。

## 9. 图族与 maturity（阶段 C 冻结，阶段 B 只验证引擎）

阶段 B 交付 `flow`（LR/TB）与 `layers` 两族，均标 `maturity: beta`；**未实现族必须优雅降级**（§3 第 6 条）。

## 11. 待裁定（推荐默认，可推翻）

1. IR 用页面级 `diagram:` 块（而不是独立文件 `/diagrams/*.yaml`）——**推荐**：与页面同源、审阅时一屏可见。
2. 引擎产出的元素 id 前缀 `d<n>_`——**推荐**：一眼看出"这块是引擎画的"，便于用户接管与回滚。
3. 结构关系**自动产出**（§6）——**推荐**：这是阶段 B 的主要收益；反对意见是"引擎产出的声明会掩盖用户的手写声明"，故引擎只产出**几何必然成立**的关系，且导出的 `groups`/`contains` 可被用户直接编辑。
4. 阶段 B 只做 `flow`/`layers` 两族，其余进阶段 C——**推荐**：先把引擎钉稳，再铺族。
5. 组级裁剪渲染先做 CLI（`ppt_render` 的 `group=` 参数随后）——**推荐**：审阅路径先通，再进工具面。
