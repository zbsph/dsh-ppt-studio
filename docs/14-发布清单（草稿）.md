## 7. 发布通道与硬规矩（2026-09-30 实测确立）

**通道**：`dsh-ppt-studio` 用 **npm Trusted Publishing（OIDC）** 发布 —— **本机没有也不该有 npm 凭据**。

| 事实 | 说明 |
|---|---|
| **只有创建 GitHub Release 才触发发布** | `publish.yml` 的触发是 **`release` 事件** ⇒ **只推 tag 不会发布**（1.2.1 首次就因此没发出去）；补发用 `workflow_dispatch` 指定 tag。 |
| 本地 `npm publish` 必然 E401/E404 | 预期行为，**不是故障**；**不得**把它的退出码当发布判据。 |
| 发布判据 = **registry 现状** | `npm view dsh-ppt-studio version` / `dist-tags` 必须显示目标版本；否则就是没发。 |
| Release 事件触发后 | 用 `gh run list` 看 `Publish to npm` 是否 success；必要时取消（撤回触发：删 Release + `gh run cancel`）。 |

**硬规矩（用户指令）**
1. **没有用户明确指令，不得创建 GitHub Release、不得打版本标签、不得改版本号** —— 创建 Release 就等于发布。
2. 每次发布前必须逐条跑通发版前检查（本文件 §1–§4）。
3. 发布后必须**从 registry 复核**，并把结果写进 `docs/03` 与发布报告。

**标准发布序列**：`npm test` 全绿 → `verify:package` / `verify:products` → 版本号 + `docs/03` 定稿 → 提交并推 `main` → 打 `v<版本>` 标签并推 → **创建 Release（附 tgz）** → 轮询 registry 至目标版本 → 两端安装升级 → 复核。

## 8. 发布 RUNBOOK（npm OIDC 专用 · 照抄执行）

> **一句话**：本包**没有也不该有**本机 npm 凭据；发布**只能**通过"创建 GitHub Release → `publish.yml` 用 OIDC 发到 npm"这条路。

### 8.1 铁律（违反即算事故）
1. **没有用户明确指令，不得**：改 `package.json` 版本号 / 打 `v*` 标签 / 创建 GitHub Release。**创建 Release = 发布**。
2. **不得用本机 `npm publish`** —— 必然 `E401/E404`，这是**设计如此**，不是故障；**永远不要**把它的退出码当发布判据。
3. **发布判据只有一个**：`npm view dsh-ppt-studio version`（与 `dist-tags`）显示目标版本。

### 8.2 标准序列（逐条执行，任一不过即停）
```powershell
# 0) 发版前检查（全绿才能继续）
npm test                        # 期望 322 通过 / 0 失败
npm run verify:package          # 打包与安装一致性（装到干净目录后 require 可用）
npm run verify:products         # 本机专用：重出 → 导出 → 渲染 13 PNG → 与基线比对

# 1) 版本与日志
#    package.json 的 version → <新版本>；docs/03 写 [<新版本>] <日期> 条目（含已知限制）

# 2) 提交并推主干
git add -A; git commit -m "release(<版本>): …"; git push origin main

# 3) 打标签（注意：**只推 tag 不会发布**）
git tag -a v<版本> -m "<一句话>"; git push origin v<版本>

# 4) 打包并**创建 Release** —— 这一步才触发发布
$tmp = Join-Path $env:TEMP ("rel" + (Get-Random)); New-Item -ItemType Directory -Force -Path $tmp | Out-Null
$tgz = (npm pack --pack-destination $tmp | Select-Object -Last 1).Trim()
gh release create v<版本> (Join-Path $tmp $tgz) -R zbsph/dsh-ppt-studio -t "dsh-ppt-studio <版本>" -n "<发布说明>"

# 5) 等发布并**从 registry 复核**（唯一判据）
gh run list -R zbsph/dsh-ppt-studio --limit 3        # 看 "Publish to npm" 是否 success
npm view dsh-ppt-studio version                       # 必须等于 <版本>
npm view dsh-ppt-studio dist-tags --json

# 6) 两端安装升级
#    web： dsh plugin --profile web add dsh-ppt-studio@<版本>
#    桌面端：应用「插件管理」界面升级（CLI 对 desktop profile 会被拒：managed exclusively by the Electron application）
#    ⇒ 桌面端升级后需**重启应用**才生效；重启后在插件管理里确认版本

# 7) 记录：docs/15 追加发布小节；docs/03 条目保持与实际一致
```

### 8.3 撤回（仅当尚未真正发布到 npm）
```powershell
gh release delete v<版本> -R zbsph/dsh-ppt-studio --yes   # 移除触发源
gh run list -R zbsph/dsh-ppt-studio --limit 5             # 找到 queued/in_progress 的 Publish run
gh run cancel <数据库ID> -R zbsph/dsh-ppt-studio          # 取消它
npm view dsh-ppt-studio version                           # 确认仍是上一版（= 未发布）
```
**一旦已发布**：**不要** unpublish（会伤消费者）⇒ 改用**发下一个补丁版本**修正。

### 8.4 补发/重发
用工作流自带的手动入口（`publish.yml` 支持 `workflow_dispatch` 并接受 tag 入参）：
```powershell
gh workflow run publish.yml -R zbsph/dsh-ppt-studio -f tag=v<版本>
```
